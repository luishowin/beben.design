Thinking in pixels

Meet Sprite

A little AI guide with a lot of character. Sprite replaces the generic website chatbox with an animated mascot that helps visitors navigate, answers questions, and adds warmth to a very technical website.

Hey, I'm Sprite - need help finding something?
The constraint

A widget with nowhere to put a key

This site is static HTML on GitHub Pages. No build step, no server, no database, nothing running between the repository and the visitor. Twenty pages carry the widget. That was not a limitation to design around, it was the brief: whatever Sprite became had to ship as two files and keep working on the day everything else did not.

A chat widget in that setting has three problems, and none of them are design problems. There is nowhere to put an API key, because anything in a public repository is public and anything the browser downloads is public. There is nowhere to hide a slow failure, because a static site has no ops page, no queue and no retry worker behind an error message; the widget itself has to decide what happens next, immediately, in front of whoever is looking. And there is no defensible reason to put a dependency tree behind a mascot.

The commercial constraint is blunter than any of that. This is the studio's own site, so Sprite is a shop window, and a shop window that dies during a client demo costs more than the feature is worth. It also sits on a metered API behind a public page with no login, which makes every architectural choice a spending choice. An uncapped proxy is an open tap, and a per-message cost attached to a portfolio mascot is a bill with no revenue standing behind it.

What lost

The versions that did not ship

None of these were straw men. Each was the obvious answer to one of the three problems, and each lost for a reason that can still be pointed at in the source.

Call the model directly from the browser, with the API key in sprite.js

It is the shortest path and it is unshippable. GitHub Pages serves the repository, so the key would sit in view-source on twenty public pages, readable by anyone and spendable until the credits ran out. No obfuscation survives a devtools tab, so this was never a hardening problem to solve later. It is a hosting model that cannot hold a secret at all.

Drop in a chat SDK and the framework it expects

The vendor widget brings a bundle, a build step and a runtime to a site that deliberately has none of the three, and it would land on all twenty pages so that a portfolio could have a mascot. It also puts the personality behind somebody else's theming layer, which is the one part of this that had to be ours. Written by hand instead, the entire widget is 1,165 lines and 52.0 KB with no external runtime dependency at all.

Let the LLM be the only brain and show an error state when it is down

An error state is a promise that somebody is watching, and on a static site nobody is: no queue, no retry worker, no ops page behind the apology. A model-only widget also has no floor under what it says about money, and this one gets asked about pricing. The pattern engine costs nothing per message, answers in zero network round trips, and cannot invent a discount, so it became the primary experience rather than the consolation prize.

Stand up a small backend of our own to hold the key and the prompt

A server is the correct answer to the key problem and the wrong answer to everything else here. It reintroduces uptime, deploys, patching and a monthly line item for a feature whose job is to say hello, and it ends the hosting story where publishing is just a push to a branch. The Cloudflare Worker that shipped is 154 lines on a free tier of 100,000 requests a day: the smallest thing that can hold a secret without becoming a system to run.

Render the model's markdown links exactly as it writes them

Give a language model a markdown renderer and it will eventually emit an href you did not want on the page. The failure mode is not a bad answer, it is a live anchor with the studio's name wrapped around it. The renderer escapes everything first and then linkifies against five explicit rules: site-relative paths, beben.design, wa.me, mailto and tel. Anything else stays plain text. The model is trusted with tone and never with a destination.

Persist the conversation in localStorage so Sprite remembers returning visitors

Memory across visits sounds like the better feature and is the wrong lifespan for a site guide. Somebody returning next week does not want last week's half-finished question sitting there waiting, and keeping it turns a navigation aid into something that has to be described in the privacy policy. sessionStorage delivers the useful half: the chat follows a visitor from the services page to the contact page and dies with the tab.

What shipped

What is running now

A page adds two includes, both carrying a version query string, and gets the whole widget. sprite.js injects its own DOM, so no page carries markup for it and no page can quietly drift out of sync with the others. Twenty pages on this site include it.

The offline brain is a dialogue table that ships inside the script: 24 intents, each a regular expression mapped to a pool of replies written by hand in Sprite's voice, 46 of them counting the three fallbacks that admit ignorance and offer the sections it does know. Replies carry suggestion chips so a visitor can keep moving with one tap. The character is 11 emotion states drawn entirely in CSS, keyframes on a few nested divs, so an expression costs no image request.

The live brain is a 154 line Cloudflare Worker sitting between the site and Fireworks AI. It holds the key as a Worker secret, assembles the system prompt, and caps what any visitor can spend: 12 messages of history, 1,000 characters each, 450 tokens of reply. CORS is locked to four origins, one of them the local preview port, so the live brain works while building and nowhere else. What Sprite knows beyond the baked-in prompt is docs/sprite.md, a markdown file served like any other page, fetched by the Worker and cached for five minutes under an 8,000 character ceiling. Teaching the mascot something new is a git push, the same motion as editing any page.

The join between the two is a single catch. Any failure of the live brain routes the message to the pattern engine and logs one console warning, once. There is no error state anywhere in the interface, because the offline brain means there was never a moment that needed one. One ordering detail is worth stating precisely, because it is the opposite of how it looks: at runtime the proxy is tried first and the pattern engine catches, but in design the sequence is reversed. The offline answers were written first and treated as the product, and the model is the upgrade layered on top of them.

  • sprite.js and sprite.css, 1,165 lines and 52.0 KB combined, with zero external runtime dependencies
  • A 24-intent offline dialogue engine, 46 hand-written replies, suggestion chips on the ones that need them
  • 11 emotion states drawn in CSS, no sprite sheet and no image request per expression
  • A 154 line Cloudflare Worker holding the Fireworks key, CORS locked to four origins, history and tokens capped at the proxy
  • A git-pushable knowledge base at docs/sprite.md, cached five minutes, capped at 8,000 characters
  • A five-rule link allowlist that renders model-written hrefs only for this site, WhatsApp, mailto and tel
  • Deploy documentation in cloudflare-worker/README.md, so the proxy is reproducible by somebody who is not us
What it produced

What can actually be counted

This site runs no analytics, so what follows is engineering measurement rather than visitor measurement. Every figure below was read out of a file with a shell command, and the commands are on the record.

2
files a page includes

sprite.css and sprite.js. The widget injects its own DOM, so no page carries markup for it.

1,165
lines across both files

787 in sprite.js, 378 in sprite.css. 52.0 KB uncompressed, before any transfer encoding.

0
external runtime dependencies

No import, no require, no script tag, no CDN host, no @import in either file. The repository has no package.json.

24
offline intents

24 regular expressions mapped to a pool of 46 replies, 43 in the dialogue table plus 3 fallbacks, all written by hand.

11
emotion states, drawn in CSS

Every expression is keyframes on nested divs. No sprite sheet, no image request, themes for free.

154
lines in the entire proxy

The whole live brain. It holds the key, builds the prompt, caps the request, and returns one JSON field.

12 / 1,000 / 450
history, chars, reply tokens

MAX_HISTORY, MAX_MSG_CHARS and MAX_TOKENS in sprite-proxy.js. The caps live at the proxy, where a visitor cannot move them.

5 min
knowledge base refresh

KNOWLEDGE_TTL_MS. Editing docs/sprite.md, currently 97 lines, and pushing changes what Sprite knows within five minutes.

20
pages carrying the widget

Every page of the main site. The arcade is the deliberate exception: it ships no Sprite so it runs fully offline.

What is not measured here

This site runs no analytics. There is no gtag, no Tag Manager, no Plausible, no Umami, no PostHog, so there are no visitor numbers on this page and there will not be any: no sessions, no conversations opened, no enquiries attributed to Sprite. The proxy is just as quiet, logging one line on an upstream error and nothing else, which means the number that would be most interesting, how often the live brain answers versus how often the pattern engine catches it, is not measured either. Everything above is a file on disk or a constant in source, read with a command before it was written down.

What's next

Roadmap

The current MVP is live and working. Here's what's coming.

Done

AI-powered live chat

Shipped. Sprite now runs on a real AI backend: it understands context, remembers the conversation as you move between pages, and answers questions it was never explicitly programmed for, personality intact. The pattern engine stays on as an offline fallback.

Next

Customisable sprites

A configuration layer that lets site owners choose their sprite's appearance, personality, colour, and default expressions. Different sites get different characters: same engine, unique identity.

Planned

Voice conversations with AI

Full two-way voice chat. Talk to Sprite, hear it respond in a synthesised voice, and watch its expressions match the conversation in real time. The current Web Speech API foundation will be upgraded to support continuous, natural dialogue.

Planned

Advanced TTS with emotion

Moving beyond the browser's default speech synthesis to an expressive TTS engine that adjusts tone, pace, and inflection based on the sprite's emotional state, so it sounds as alive as it looks.
